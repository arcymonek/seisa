## For developers and forks

Everything you need to decide about a fork and to work on one is in this documentation (this page, [Architecture and design](architecture.md) and [API reference](api.md)); the README is the short entry point. The two files directly in `docs/` are prompt context for the LLM, summarised where they matter (the [AbuseIPDB](tabs.md#abuseipdb) and [Email](tabs.md#email) tabs).

### Should you fork?

Seisa is free software under the [GPL-3.0-or-later](../../LICENSE), so a fork is always allowed. Before you start one, consider sending the change upstream instead: pull requests are welcome (see [CONTRIBUTING.md](../../CONTRIBUTING.md)).

| You may | You must |
|---|---|
| use, study, copy, change and distribute Seisa (forks included), for any purpose, commercial use too | keep a modified version you distribute under the same license (GPL-3.0-or-later or, at your option, a later version) and give the recipients its source code |
| sell copies or offer support for it | keep the copyright and license notices (`LICENSE`, the notice in the README) and say that you changed it |

A fork is a reasonable choice if you want to keep a local, dependency-light tool and adapt it: add a threat-intel source, a language, a tab, another LLM provider. It is a poor choice if you need multi-user access, authentication, remote hosting or a database; those are non-goals (see [Design decisions and non-goals](architecture.md#design-decisions-and-non-goals)).

### How to extend

#### Add a threat-intel service

1. `backend/services/<name>.py`: subclass `IntelService` (`backend/services/base.py`) with a `name`, `query_ip` and `query_domain`; use `fetch_json` for HTTP so errors are readable and rate-limit headers are observed.
2. Register it in `SERVICE_REGISTRY` in `backend/aggregator.py`.
3. Add its key to `Settings` in `backend/config.py` and to `.env.example`; show its status in `backend/routers/about.py`.
4. If it should influence the score, add a `CREDIBILITY` entry and a `score_<name>` function in `backend/scoring.py` and register it in `compute_risk_score`.
5. Frontend: the service metadata in `frontend/js/lookup-result.js` and the `ALL_SERVICES` list in `frontend/js/lookup.js`; Markdown: the title and `SERVICE_ORDER` in `backend/markdown_report.py`.
6. Optionally its free-plan limit in `backend/api_limits.py`.
7. i18n keys (`md.service.<name>` and any messages) in both catalogs; a mocked answer in `scripts/api_harness.py`; run the checks below.

#### Add a language

1. Add `frontend/i18n/<xx>.json` and `backend/locales/<xx>.json` with the same keys as the English ones (`scripts/check_i18n.py` compares keys, `{placeholders}` and plural forms; the required plural suffixes per language are in `PLURALS_REQUIRED` there).
2. Add the language to `SUPPORTED` and `LOCALES` in `frontend/js/i18n.js` and to `SUPPORTED` in `backend/i18n.py`.
3. The LLM prompts are single and in English; extend the label table and the language directive in `docs/email-analysis-guide.md` for the new language.
4. Translate the README and `docs/en/` (into `docs/<lang>/`) under the same heading structure.

#### Add a colour theme

1. Copy `frontend/themes/light.json` (or `dark.json`) to `frontend/themes/<id>.json` and change the values. `id` must equal the file name (lowercase letters, digits and `-`), `base` is `light` or `dark` (it sets the browser's `color-scheme` for form controls and scrollbars), `order` sorts the theme buttons (light is 10, dark 20, kohaku 30; "System" is always last), `name` holds the button text per language. The header logo follows `base`: `logo.png` (dark badge) on a dark theme; on a light one it is the shape in `logo-mask.png` painted in the theme's accent colour (no badge, so it sits directly on the page background). Optionally `stripe` adds a two-tone bar under the page header: `{"top": "#rrggbb", "bottom": "#rrggbb"}`, exactly these two keys; a theme without it has no bar.
2. `colors` must contain exactly the keys of `COLOR_KEYS` in `backend/themes.py`, each as `#rrggbb`: nothing missing, nothing extra, no other CSS. A file that breaks a rule is skipped and the reason goes to the log. The key `info` is the border of information banners: use your accent colour when it is not red, and a neutral colour otherwise, so that information cannot be mistaken for an error.
3. Reload the page: the new theme appears as a button in Info > Settings. Keep text readable: `tests/test_themes.py` shows the pairs that need a 4.5:1 contrast (WCAG AA) for the shipped themes; run `python3 -m pytest -q tests/test_themes.py`.
4. For a new colour in the interface, add a key to `COLOR_KEYS`, to every shipped theme and use `var(--key)` in `style.css`; never write a colour literal in the stylesheet (a test checks that).

#### Add a tab

1. A button and a `<section>` in `frontend/index.html`; the panel in `frontend/js/app.js`.
2. One module in `frontend/js/` in the style of the neighbours (ES modules, no framework), with its texts in the catalogs.
3. A router in `backend/routers/` included in `backend/main.py` if it needs a backend; a place in the harness.
4. Follow the shared layout (verdict banner, tiles, collapsible cards) and the action row: the timer, the status and related buttons sit next to the action button.

### Workflow, tests and conventions

- **Verification:** `./.venv/bin/python scripts/api_harness.py` runs every endpoint against mocked services (no keys, no network) and exits with 1 on an unexpected answer, a request that left the mocks, or a failed security probe. `--out file.json` writes the normalised answers and `--root` points at an older checkout (`git archive`): after a refactor the two versions must give the same output. `scripts/dump_facts.py` and the synthetic `tests/fixtures/*.eml` do the same for the deterministic e-mail analysis (after changing texts in `email_forensics.py` the dump in `pl` must stay identical; both scripts read only the flat `tests/fixtures/*.eml`, not the `unit/` subfolder). The interface is checked by hand.
- **Unit tests:** `./.venv/bin/pip install -r requirements-dev.txt`, then `./.venv/bin/python -m pytest -q` (a few seconds for the unit tests, about two minutes more with the hook tests of `tests/test_pre_commit_hook.py`, which build throw-away git repositories and are marked `slow`: `pytest -m "not slow"` skips them; no network, no keys). `tests/conftest.py` points `data/` and `logs/` at a temporary directory and fails the run if the real ones changed. Expected values are worked out from the RFCs and by reading the sample e-mails, never copied from the program's own output; a test that exposes a real defect is marked `xfail(strict=True)` with the reason instead of being bent to match. To add a case, save a SYNTHETIC `.eml` in `tests/fixtures/unit/` (reserved addresses only) and assert what its headers prove. Real messages belong in the gitignored `tests/private/`, sorted into `legit/` (genuine) and `phishing_spam/`: the folder alone checks that a genuine message never looks spoofed and that every message is analysed without an error, and a `name.expected.json` next to a message adds exact expectations (format at the top of `tests/test_corpus.py`); without any message that test is skipped.
- **Linting:** `ruff check backend scripts tests` (installed by `requirements-dev.txt`, pinned to one minor series so that a new ruff release does not suddenly report new findings in unchanged code; configuration in `pyproject.toml`; a development tool, not a dependency). For a frontend module: `cp file.js $TMPDIR/x.mjs && node --check $TMPDIR/x.mjs`.
- **CI:** `.github/workflows/ci.yml` (GitHub Actions) repeats the local set above on Linux, on Python 3.11 and on the latest 3.x: `ruff check`, `pytest`, `api_harness.py`, `check_i18n.py --strict` and `dump_facts.py`. It runs on pull requests and on pushes to `main`. For a pull request from a fork it skips the version rule (the maintainer adds the version bump after review), and still checks the lines the branch adds for a long dash and private data. A green run does not replace running the set locally, does not prove that the tests cover your change, and does not check the interface in a browser. In a fork on GitHub the same workflow runs once Actions are enabled there.
- **Git hooks:** `scripts/hooks/pre-commit` checks what is staged before every commit (about two seconds): no forbidden files (`CLAUDE.md`, `.env`, `data/`, `logs/`, `tests/private/`, `reports/`; they are gitignored, so this only catches `git add -f`), no long dash in added lines, the README and `docs/en`/`docs/pl` files staged in pairs, `check_i18n.py --strict` run on the staged versions (so a half-staged change is judged as it will be committed), a privacy scan of the added lines (no API-key-looking strings, no home directory paths, none of your own host or domain names) and a version that, if it differs from the one on `main`, is exactly one allowed step away (so a branch cannot bump twice) and comes with its `## X.Y.Z - YYYY-MM-DD` entry in `CHANGELOG.md`, dated like `seisa-release-date` in `frontend/index.html`. `scripts/hooks/commit-msg` checks the message: no long dash, no `Co-Authored-By` trailer, no "Generated with Claude Code" footer, and the same privacy scan. Your own names live in a file OUTSIDE the repository, `~/.config/seisa/privacy-markers.txt` (or the file named by `SEISA_PRIVACY_MARKERS`): one name per line, `#` for comments, and a line starting with `!` is a string that is allowed (for example the author's public contact data) and is removed before scanning; without the file only the generic checks run and a note says so, and a match never prints the value. Enable the hooks once per clone with `git config core.hooksPath scripts/hooks`; git hooks are not versioned, this setting is what points git at the versioned copy. A fix in one language only: `SEISA_ONE_LANG=1 git commit ...` skips just the pair rule. Git itself does not run `pre-commit` for a rebase or a merge, so those are covered only by the next check. `python3 scripts/hooks/pre-commit --range main` checks the whole branch: when program files changed the version must have gone up by one step, when none did it must not have (CI runs it on pull requests); it also applies the long dash rule and the privacy scan to every line the branch adds, because a fork runs no hooks (commit messages are not judged there), and `--no-version-rule` checks only those lines. A change that really needs no bump (comments only) says so with a `No-version-bump: <reason>` line in a commit message of the branch. `tests/test_pre_commit_hook.py` breaks every rule on purpose in throw-away repositories, also through real `git commit` (partial commits, `-a`, `--amend`) and on a simulated pull request merge commit, and expects the hooks to refuse.
- **i18n:** every text visible to the user goes through the catalogs (`t()`/`tn()` in the frontend, `backend/i18n.py` in Python). A new key needs a PL and an EN entry; run `python3 scripts/check_i18n.py` (also checks README and `docs/` heading parity, dead relative links and anchors, and that the version is the same in all five places) and look at the UI in `/?lang=qa`. Catalogs hold plain text; never HTML.
- **Versioning:** the version tracks the program, not the repository. It changes only when the program changes (`backend/`, `frontend/`, `requirements.txt`, `requirements.lock`, `seisa.sh` and the two prompt-context files directly in `docs/`), by exactly one step: the last number +1 for a fix or changed behaviour (no upper limit: after 2.0.99 comes 2.0.100), the middle number +1 and the last back to 0 for a new feature, tab, external service or `.env` key; the first number only by the author's decision. Documentation, tests, scripts, CI and comment-only changes leave it alone, and a branch bumps it once, in its last commit. The version is in five places: the `<title>`, the header and the footer of `frontend/index.html`, and under the logo in both READMEs. The release date (`YYYY-MM-DD`) in `<meta name="seisa-release-date">` of `index.html` is updated with every release; the Info tab shows it under the version. Add an entry to [CHANGELOG.md](../../CHANGELOG.md). Version 2.0.0 is the first release under the name Seisa.
- **Documentation:** the short `README.md` (English, the main one) and `README.pl.md` (Polish), and the pages of `docs/en/` and `docs/pl/` (the same file names, the same heading structure) change together; the two files directly in `docs/` are prompt context, not documentation.
- **Language and style:** code, comments, docstrings, log messages and commits are in English; the whole project avoids the long dash (Unicode U+2014), only a plain "-".
- **Action rows:** every tab that runs an action shows the timer (always one decimal, for example `13.1 s`), the status (for example the loaded file) and related buttons in one row next to the action button, during and after the run; in the Email tab the tokens and cost sit there too.
- **OpenRouter:** never guess a model slug or prices; the cost comes from the `usage.cost` that OpenRouter returns (`"usage": {"include": true}`).
